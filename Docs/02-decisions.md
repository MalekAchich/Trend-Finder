# 02: Decision Log

**Status:** Draft v1. Add new decisions at the bottom; never silently rewrite old ones (mark them superseded).

| ID | Decision | Why |
|---|---|---|
| D-01 | **Local, personal, single-user app.** | Owner-only tool; no hosting, auth or multi-tenancy needed. |
| D-02 | **Models come from the owner's Claude and ChatGPT subscriptions** via the owner's existing auth code. Cost per run is $0 within the usage windows (reset every ~5 h). | Owner decision. Both accounts are paid and dedicated to this. |
| D-03 | **Each provider is behind one adapter interface; a CLI-subprocess adapter (`claude -p`, `codex exec`) is a drop-in fallback.** | If a provider changes how subscription auth is treated, switching becomes a config change instead of a rewrite. |
| D-04 | **Multi-agent master/worker architecture.** A Master agent ingests the inputs, decides how to divide the work, and spawns N parallel workers with disjoint tasks, over multiple rounds. | Owner requirement: real parallel multitasking, not one agent. Same pattern as leading deep-research systems. |
| D-05 | **The Master is a decision step called at round boundaries, not a long-lived chat.** The deterministic orchestrator executes its plans. | Keeps the Master's context small, makes runs resumable after a crash, and puts caps/limits outside any model's control. |
| D-06 | **Workers cannot spawn workers.** They return *leads*; the Master assigns them in the next round. | Prevents runaway fan-out and duplicate work. |
| D-07 | **Non-redundancy is enforced by the orchestrator**, through scope ownership plus a shared blackboard (seen videos, done queries, leads). | Prompts alone don't reliably prevent overlap. |
| D-08 | ~~Agent loop: custom loop by default; PydanticAI if compatible.~~ **Superseded by D-30.** | Both providers use non-standard subscription endpoints that most frameworks don't support. |
| D-09 | **No RAG / knowledge base in v1.** Feedback is stored as structured rows plus a versioned per-character taste profile, plus best/worst examples placed directly in prompts. | Feedback volume fits in the context of current models. Revisit at ~500 rated findings or cross-character learning. |
| D-10 | **PostgreSQL uses the `pgvector` image from day one**, but no embeddings in v1. | Free to include; removes a migration later (D-09). |
| D-11 | **Platforms: TikTok, Instagram Reels, YouTube Shorts.** | Owner requirement. |
| D-12 | **Scraping is a tool layer the agents call.** Agents choose inputs and read structured JSON; they never parse HTML. Each platform is isolated, rate-limited and circuit-broken. | Agents spend reasoning on judgment; a broken scraper only takes down its own platform. |
| D-13 | **TikTok and Instagram are accessed through Playwright with persistent, logged-in throwaway accounts**, reading the app's JSON responses rather than the page's HTML where possible. Shorts uses the official YouTube Data API. yt-dlp fetches metadata/media for any URL. | Login walls and anti-bot measures; JSON responses are more stable than page HTML. |
| D-14 | **Self-hosted SearXNG for general web search.** | Free, no API key, no per-search fee. |
| D-15 | **Deterministic video pipeline before any AI judgment:** ffprobe, scene-aware frame sampling, contact sheet, faster-whisper transcript, MediaPipe pose. | Cheap evidence. The pose-based feasibility filter skips expensive judging of unusable videos. |
| D-16 | **The AI judge sees one contact-sheet image per video** (a grid of key frames), not many separate frames. | About 10× less usage per judgment with little loss of information. |
| D-17 | **The match score is split into sub-scores** (character fit, Kling feasibility, momentum, freshness) with a weighted overall score. Source status is a label, not a weight. | Explainable, tunable from feedback, and debuggable. |
| D-18 | **Explore/exploit via per-direction Beta stats (Thompson sampling).** The last overall satisfaction score sets the share of new directions. | Makes "more creative vs. narrower" measurable and repeatable. |
| D-19 | **Findings are grouped into trend clusters** (video fingerprint + shared sound + AI confirmation). One card per trend, with the cleanest version marked as the motion reference. | The same trend appears across hundreds of reposts. |
| D-20 | **Top-K findings get a blind second opinion from the other provider.** Large disagreements are flagged. | Reduces single-model taste bias; puts both subscriptions to use. |
| D-21 | **Production briefs are generated only on 👍**, on demand. | Saves usage for findings the user actually wants. |
| D-22 | **Stopping is rule-based and enforced by the orchestrator** (target findings above threshold, budget, rounds with no new results, wall clock). The Master may stop earlier, never later. | Agents left to judge their own satisfaction stop too early or never. |
| D-23 | **PostgreSQL is also the job queue** (`FOR UPDATE SKIP LOCKED`). No Redis/Celery. | One fewer service; enough for a single machine. |
| D-24 | **Backend: Python 3.12 + FastAPI + asyncio workers. Frontend: Vite + React + Tailwind + shadcn/ui.** | Owner chose FastAPI; no server-side rendering is needed, so Vite is simpler than Next.js. |
| D-25 | **Docker Compose runs Postgres and SearXNG only; backend and frontend run natively.** | Playwright needs a visible browser for one-time manual logins; running natively also makes development easier. |
| D-26 | **Media storage has a quota (default 5 GB) with automatic cleanup.** Full videos are kept only for 👍 findings; contact sheets and metadata are kept for everything. | Only ~19 GB of disk is free on the dev machine. |
| D-27 | **Source license status is recorded and shown, never used as a filter.** | Owner takes responsibility for sourcing choices. |
| D-28 | **No n8n or any workflow platform.** | Owner decision. |

| ID | Decision | Why |

| D-29 | **Claude is called through the official `claude -p` CLI subprocess** (`--tools ""`, `--json-schema`, `--no-session-persistence`, images via `@file`). Login/status uses `claude auth …`. **ChatGPT is called through OAuth (PKCE/device code) with direct HTTP to `chatgpt.com/backend-api/codex/responses`** (Responses API over SSE), with tokens in our own `secrets/chatgpt-auth.json` (chmod 600). Implementation follows `Code docs/claude-codex-auth-reference.md`. | Owner's proven code. The app logs in to ChatGPT on its own, separate from `~/.codex/auth.json`, so refresh-token rotation never breaks the owner's Codex CLI. |
| D-30 | **Custom agent loop (no framework).** ChatGPT uses native Responses tool calling. Claude uses **emulated tool calling** enforced with `--json-schema` (step format in D-36). | Neither provider exposes a standard client, so frameworks don't fit. One loop with two step-protocols keeps the agents provider-agnostic. |
| D-31 | **Claude calls are stateless per step.** The loop re-sends a compacted transcript each step. Claude steps run with a per-call timeout (default 180 s) and a process cap equal to the provider concurrency. | `--no-session-persistence` means no server-side memory; subprocess fan-out must be bounded. |
| D-32 | **Repository uses the owner's folders.** `Database/` = Postgres + SearXNG compose, SQLAlchemy models and Alembic migrations (package `tf_db`). `Agent/` = the multi-agent engine: model layer, loop, roles, prompts, tools, pipeline, scoring, orchestrator (package `tf_agent`). `Backend/` = FastAPI API, SSE, `tf` CLI (package `tf_backend`). `Frontend/` = Vite React app. One **uv workspace** at the app root ties the three Python packages together. | Owner prepared these folders for a clean architecture. |
| D-33 | **Niche discovery is a job for the agents** (since D-38 the niche is always open: the Reader proposes hypotheses). When `profile.md` marks the niche `OPEN`, the Master spreads explore directions across distinct niche hypotheses, and every direction carries a `niche` tag. Once a niche earns consistent 👍, the Learner proposes it as the primary niche in the taste profile. | Owner decision: the system finds the niche. |
| D-34 | **Platform tools work anonymously first; logged-in sessions are an optional upgrade.** Discovery without accounts uses: SearXNG `site:` queries (tiktok.com, instagram.com/reel, youtube.com/shorts), yt-dlp for metadata of any found URL, yt-dlp `ytsearch` (filtered to ≤ 3 min) for Shorts, TikTok Creative Center (public), and logged-out TikTok web pages through Playwright where they work. Logged-in Playwright profiles and the YouTube Data API key plug in later through config, with no code changes. | Owner has no throwaway accounts or API key for now; the YouTube key is a later "launch factor". |
| D-35 | *(Superseded by D-38: there is no profile.)* **The character's own social accounts are an input signal** (`profile.md` → `socials`), read for insights once they exist. They are never used as scraping sessions. | Owner will add Nicolaiz's TikTok later. |
| D-36 | **Every Claude CLI call runs isolated:** `--strict-mcp-config --mcp-config <empty> --setting-sources ""`, a custom `--system-prompt`, a neutral working directory, the prompt via **stdin** (never argv), and images as `@<space-free path>`. Emulated tool steps return `{"note"?, "calls":[{name, arguments}]}` (a one-line progress note; asking Claude to "think out loud" into a `thought` field trips its reasoning-extraction safeguard, found live 2026-10-06); `submit_result` is a normal tool, so ChatGPT and Claude follow the same protocol. | Measured 2026-10-05: default `claude -p` costs ~70k context tokens per call (Claude Code prompt + plugins); isolated costs ~2.7k (≈25× less usage). Linux limits a single argv to 128 KB. `@` mentions break on spaces, and the app folder has spaces. |
| D-37 | **The usage governor reads ChatGPT's `x-codex-*` response headers** (`primary-used-percent`, `primary-window-minutes`=300, `primary-reset-at`, and the weekly `secondary-*`) and pre-emptively cools the provider at ≥ 98% used. Claude limits are detected from CLI error results. | Measured 2026-10-05: exact usage and reset times are returned on every ChatGPT call. |
| D-38 | **A character is only its images.** No profile, persona or niche text exists anywhere. Each run starts with the **Reader** vision role, which turns up to 4 images (+ taste profile + owner notes) into a `CharacterRead`; the brief every role receives is rendered from it. | Owner (2026-10-06): "the character are only the image provided"; the agents must discover vibe, niche and targets themselves. |
| D-39 | **One page, one hybrid theme.** No sidebar, menu, tabs or logo. Dark top (composer + live engine), light bottom (found videos), joined by an animated seam; a saved video "travels" from the engine into the library. Briefs and Settings are gone. | Owner direction plus the reference UI export. |
| D-40 | **Videos are kept as URL + metadata + one ≤ 40 KB thumbnail.** Downloads exist only for the analysis and are deleted right after; contact sheets are deleted after the run's curation. Hover previews use the platforms' own embed players. | Owner: "we would just save the URL so no space". |
| D-41 | **The owner steers runs with URLs:** trending AI-influencer videos (studied for formats before round 1) and target videos tagged with a character (analysed directly in that character's next run). | Owner request. |
| D-42 | **Feedback is per video and immediate** (👍/👎 + optional note, changeable any time), plus an optional 1–10 score per finished run. Scoring weights are fixed in code. | Fits the single page (no review step); weights/settings confused the owner. |
